## Step 6 — Upload resilience (M4)

- Date: 2026-10-12
- Status: done
- Summary: Sessions now persist to `.model_crud_<id>.json` (atomic, `fsync`ed, rewritten under a per-session lock after each recorded chunk, coalesced when a newer save covers an older one) and are rebuilt from disk at server start, before the server accepts requests (`app.on_startup`, `on_cleanup` stops the sweep). `GET /model_crud/uploads/{id}` returns `received_ranges`, `GET /model_crud/uploads` lists sessions. Per-chunk SHA-256 (`Upload-Chunk-SHA256`, hashed in the worker thread while streaming, 422 on mismatch) and optional whole-file `sha256` on complete (worker thread, 422 with the session and temp file kept). Idle sessions expire at startup and then hourly (`asyncio` task, cancelled cleanly); every chunk request, including failing ones that reach the body, refreshes `expires_at`.
- Security design of the restore path: nothing in a sidecar is trusted. The target is re-resolved through the normal resolver, must equal the directory the sidecar sits in (and belong to the scanned root), the `.part` must be a regular file (not a symlink) of the declared size, and ids, sizes, times and ranges are range-checked (chunk count capped at 1 000 000, sidecar size at 1 MiB). Failures delete only files named `.model_crud_<that id>.*` in that directory. Orphans without a sidecar are removed only if older than 1 hour. The scan covers the root plus four levels of visible, non-symlinked folders of managed keys.
- Invariant added: a chunk is "received" only while its byte range holds that complete (and verified) chunk, so a re-send un-records the chunk and persists that before writing the first byte. This closes a Step 5 gap where an aborted or corrupt re-send of an already recorded chunk left damaged bytes marked as received.
